# Architecture

SeleSele is a modular Nuxt/Bun application with MySQL. An **item** has exactly one immutable kind: `document`, `kanban`, `whiteboard`, or `diagram`. Folders organize items inside a workspace. Members, groups, grants, archives and Trash share the same access policy across HTTP, collaboration, search, AI, media, export and recovery.

## Boundaries and dependency injection

- `shared/model`: the single canonical vocabulary for values, snapshots, messages and pure policies. There are no contract/kernel passthrough files.
- `shared/validation`: strict request schemas, independent of browser/server adapters.
- `server/features/<feature>/domain`: entities, policies and dependency ports. No framework, HTTP, database or provider imports.
- `server/features/<feature>/application`: constructor-injected use cases, authorization and orchestration. No SQL, filesystem, framework, or provider implementations.
- `server/features/<feature>/infrastructure`: adapters implementing domain ports.
- `server/platform`: database, HTTP, document protocol and runtime adapters.
- `server/bootstrap/modules`: explicit runtime, authentication, workspace, communication, content, knowledge and background composition modules.
- `server/bootstrap/application.ts`: the single composition root and process lifecycle. Routes obtain `getApplication().services`; domain/application classes never resolve dependencies globally.
- `app/features`: typed API clients, framework-independent editor commands and feature presentation.
- `app/core/realtime`: a query dependency catalog, coalescing registry and browser transport. Vue composables bind their lifecycle to these classes.
- `app/plugins/api.ts` and `app/plugins/realtime.ts`: per-application/request browser composition; no shared SSR user state.
- `app/pages`: Nuxt route adapters. Framework route terminology does not rename the item entity.

ESLint enforces dependency direction. Knip checks unused files, exports and dependencies. New business rules belong in application/domain classes, never SQL triggers or view templates.

## Database and transactional change capture

`drizzle/0000_schema.sql` is the complete development baseline. `drizzle/0001_realtime_capture.sql` installs infrastructure change capture generated by `scripts/support/changeCapture.ts`. This rewrite intentionally starts from a new schema; development reset deletes previous accounts, sessions and workspace data.

Tables use plural snake_case names and columns use snake_case; TypeScript properties use camelCase. Content belongs to `items`, `item_documents` and `item_canvases`; conversations, document images, preferences, attachments, relations and presence use their corresponding canonical names. There is no parallel page/content compatibility model or old migration chain.

Capture triggers insert **invalidation metadata only** into `realtime_events` within the source transaction. A rollback rolls back its invalidation. Projection and infrastructure tables are explicitly excluded and tested for coverage. Membership removal also targets the removed user, allowing their browser to clear workspace state after access disappears.

An event is assigned a sequence only after its source transaction commits. A serialized `realtime_clock` row prevents a slow transaction from being skipped behind a later committed transaction. Dispatchers use short transactions and skip locked source events. Each application process independently reads the committed sequence, so one process publishing an event does not consume it for another process.

The dispatcher runs every 200 ms and batches/coalesces changes. Published records expire after one day. These are change signals, not an audit history; `workspace_activity` is the audit history. Reconnecting clients obtain fresh authorized snapshots rather than depending on indefinite event retention.

## One browser invalidation connection

Each signed-in application owns one authenticated `/api/realtime/events` SSE connection. The feed carries workspace scope and topics, never item content, private object IDs, answers, attachment bytes, or membership details. Personal favorites, saved searches, notifications and conversations are delivered only to their owner. Public workspace changes are delivered only to current active members. Every snapshot endpoint independently rechecks current access.

`useRealtimeQuery` registers each server-backed query with `RealtimeQueryCatalog`. The registry refreshes matching active queries once even if several components share a cache key. Changes during a fetch schedule a trailing fetch. Hidden queries that have never been loaded stay idle. `useRealtimeEffect` covers stateful discussions, file panels, presence and active AI conversations.

A ready/reconnect event refreshes all mounted snapshots. Returning online or to a visible browser tab also refreshes snapshots and revalidates the session. SSE sends keepalives and rechecks authentication every five seconds. Revoked snapshots are cleared on 401/403/404. Membership, policy, item deletion and archive changes update the active editor and navigation without a manual page refresh.

## Content, drafts and collaboration

Document peers use the standard Yjs sync/awareness WebSocket protocol. Each created document has one persisted canonical initial state. Writes merge Yjs state under the item lock and recompute the matching Markdown projection. Process-local rooms consume committed state updates and broadcast remote CRDT updates without writing them back, avoiding feedback loops. Document awareness is shared through expiring `document_presence` records; structured editors use `canvas_presence`. Shared MySQL allows peers on different application processes to converge.

Structured editors use `CanvasSession`, immutable board/scene/graph commands, autosave, revisions and a three-way merge by object ID/property. Independent changes merge; overlapping changes preserve the local draft for review. Merged snapshots are revalidated for task dependencies, WIP limits, connector endpoints and content bounds. Undo history is rebased on remote snapshots rather than replacing someone else's work.

Inline fields and settings reconcile untouched fields while retaining unsaved local input. Task details preserve stale drafts and require review. Access-policy editing detects incoming policy changes and requires loading the latest policy before overwriting. AI streaming retains the user's question and does not replace an in-flight answer with a refresh. Source changes cause existing answers to be revalidated/redacted.

Local canvas backups are scoped to user/item, validated on restore, and expire after 30 days. They supplement server persistence. Archives block writes; Trash restoration and permanent purge apply the same access policy. Item versions, templates and exports use kind-specific snapshots. Attachment downloads and previews always recheck item access.

## Presentation

`ItemHeader` owns breadcrumbs, favorites and item visit tracking for all item kinds, including read-only documents. `AppHeader` owns the workspace connection indicator and notification inbox. Favorite stars use outline/filled states with the same dimensions as other header icons. Editor toolbars share primitives and semantic spacing tokens. Fullscreen expands content inside the application.

Static dimensions belong to `app/assets/css/tokens.css`; runtime canvas geometry remains numeric. Feedback uses shared toast notifications and retry actions. Structured renderers cull offscreen objects while full-scene exports retain them. Feature components compose these primitives rather than defining separate style systems.

## Operations and verification

All application processes must use the same MySQL database, `AUTH_SECRET` and persistent image storage. Reverse proxies must support WebSocket upgrades and unbuffered SSE. Multiple processes can share the feed, content and presence; migrations run once before application startup. SMTP delivery continues to use its leased transactional outbox and revalidates access/preferences before delivery.

Shutdown stops background jobs, flushes document state/presence, closes realtime subscriptions and then closes the database. `bun run verify` runs schema/dead-code/style/architecture checks, app/server types, unit tests, production build and isolated integration suites. `test:realtime` starts two real application processes and checks event coverage, privacy, rollback, late commits, document convergence/presence and cross-process revocation. Browser UI scenarios run separately with `bun run test:ui` in CI; interactive local checks use the actual UI.
